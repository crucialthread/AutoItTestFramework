Getting Started

Usage

If you installed AutoIt Test Framework via the provided installer, all files are placed in an AutoIt's include directory and can be referenced from any project:

#include <TestFramework.au3>

If you placed the files manually rather than using the installer, use the quoted form with a relative or absolute path:

#include "TestFramework.au3"

Anatomy of a Test File

A typical test file using AutoIt Test Framework follows this structure:

1. Include the framework and the code under test

#include <TestFramework.au3>
#include "MyLibrary.au3"

2. Declare a script name constant

Declare a constant holding the test file name. This is passed to _TestFmkAssert() and _TestFmkRunAllTests() so that failure output correctly identifies which file an assertion came from, which is especially useful when multiple test files are included and run together. 

Local Const $MY_LIB_TESTS = "MyLibraryTests.au3"

3. Write one function per test group

Each test function calls _TestFmkHeader() once at the top to label the group, then one or more _TestFmkAssert() calls to verify behavior. Always capture the result of the function under test into a local variable before asserting - calling the function directly inside _TestFmkAssert() calls it twice, which can consume extra stub returns or trigger unexpected side effects. Always pass the actual value and the expected value as the 3rd and 4th arguments so that failures show exactly what went wrong. 

Func _TestAdd()
    _TestFmkHeader("Test: Add() - returns correct sum")
	
    Local $vResult1 = Add(1, 2)
    Local $vResult2 = Add(-1, 1)
    Local $vResult3 = Add(0, 0)
	
    _TestFmkAssert($vResult1 = 3, "Add(1, 2) returns 3",   $vResult1, 3, $MY_LIB_TESTS)
    _TestFmkAssert($vResult2 = 0, "Add(-1, 1) returns 0",  $vResult2, 0, $MY_LIB_TESTS)
    _TestFmkAssert($vResult3 = 0, "Add(0, 0) returns 0",   $vResult3, 0, $MY_LIB_TESTS)
EndFunc

4. Build a test suite function using _TestFmkRun()

Use _TestFmkRun() to execute a test and accumulate its pass/fail result into a cumulative $bAllPassed variable. Once any test fails the accumulated state becomes False and stays False, but every test still runs giving you a complete picture in one run. 

Func _RunMyLibraryTests($bWriteSummary = True)
    Local $bAllPassed = True
	
    $bAllPassed = _TestFmkRun(_TestAdd,      $bAllPassed)
    $bAllPassed = _TestFmkRun(_TestSubtract, $bAllPassed)
    $bAllPassed = _TestFmkRun(_TestMultiply, $bAllPassed)
	
    If $bWriteSummary Then _TestFmkSummary()
    Return $bAllPassed
EndFunc

Tip: Accept a $bWriteSummary parameter so the test suite function can be called without printing a summary when included in a script that includes all test files.

5. Call _TestFmkRunAllTests() at the bottom

_TestFmkRunAllTests() runs the test suite only when the script is executed directly, not when it is included by another script. Pass the test suite function and the script name constant so the framework knows when to run. 

_TestFmkRunAllTests(_RunMyLibraryTests, $MY_LIB_TESTS)

Complete Worked Example

This example tests a small custom math library, showing a realistic test file from start to finish.

MathLib.au3 (the code under test)

; A simple math library
Func Add($a, $b)
    Return $a + $b
EndFunc

Func Divide($a, $b)
    If $b = 0 Then Return SetError(1, 0, 0)
    Return $a / $b
EndFunc

MathLibTests.au3 (the test file)

#include <TestFramework.au3>
#include "MathLib.au3"

Local Const $MATH_LIB_TESTS = "MathLibTests.au3"

Func _TestAdd()
    _TestFmkHeader("Test: Add() - returns correct sum")

    Local $vResult1 = Add(2, 3)
    Local $vResult2 = Add(-1, 1)
    Local $vResult3 = Add(0, 0)

    _TestFmkAssert($vResult1 = 5,  "Add(2, 3) returns 5",   $vResult1, 5,  $MATH_LIB_TESTS)
    _TestFmkAssert($vResult2 = 0,  "Add(-1, 1) returns 0",  $vResult2, 0,  $MATH_LIB_TESTS)
    _TestFmkAssert($vResult3 = 0,  "Add(0, 0) returns 0",   $vResult3, 0,  $MATH_LIB_TESTS)
EndFunc

Func _TestDivide_ReturnsResult()
    _TestFmkHeader("Test: Divide() - returns correct result")

    Local $vResult1 = Divide(10, 2)
    Local $vResult2 = Divide(7, 2)

    _TestFmkAssert($vResult1 = 5,   "Divide(10, 2) returns 5",   $vResult1, 5,   $MATH_LIB_TESTS)
    _TestFmkAssert($vResult2 = 3.5, "Divide(7, 2) returns 3.5",  $vResult2, 3.5, $MATH_LIB_TESTS)
EndFunc

Func _TestDivide_DivideByZero()
    _TestFmkHeader("Test: Divide() - sets @error on divide by zero")

    ; Capture @error immediately before any other call resets it
    Divide(1, 0)
    Local $iErr = @error

    _TestFmkAssert($iErr = 1, "Divide(1, 0) sets @error = 1", $iErr, 1, $MATH_LIB_TESTS)
EndFunc

Func _RunMathLibTests($bWriteSummary = True)
    Local $bAllPassed = True

    $bAllPassed = _TestFmkRun(_TestAdd,                  $bAllPassed)
    $bAllPassed = _TestFmkRun(_TestDivide_ReturnsResult, $bAllPassed)
    $bAllPassed = _TestFmkRun(_TestDivide_DivideByZero,  $bAllPassed)

    If $bWriteSummary Then _TestFmkSummary()
    Return $bAllPassed
EndFunc

_TestFmkRunAllTests(_RunMathLibTests, $MATH_LIB_TESTS)

Testing Scripts with GUI and User Interaction

When a script calls AutoIt built-ins that require user interaction or return values that affect program flow (such as dialogs, file system, registry, or GUI functions), those built-ins would execute for real during a test run. AutoIt Test Framework provides Testable.au3 and stubs to handle these cases by intercepting those built-ins during tests, making such code testable without anything actually executing.

Step 1 - Use _Tstbl_* wrappers in your script

Include Testable.au3 in your script and replace AutoIt built-in calls with their _Tstbl_* equivalents. The wrappers behave identically to the built-ins in normal use, the only difference is that they can be intercepted by stubs in tests. 

; FileCleanup.au3

#include <Testable.au3>

Func DeleteFileWithConfirmation($sPath)
    If Not _Tstbl_FileExists($sPath) Then
        _Tstbl_MsgBox($MB_OK + $MB_ICONERROR, "File Cleanup", "File not found:" & @CRLF & $sPath)
        Return False
    EndIf

    Local $iResult = _Tstbl_MsgBox($MB_YESNO + $MB_ICONQUESTION, "File Cleanup", _
        "Are you sure you want to delete:" & @CRLF & $sPath & "?")

    If $iResult = $IDYES Then
        _Tstbl_FileDelete($sPath)
        _Tstbl_MsgBox($MB_OK + $MB_ICONINFORMATION, "File Cleanup", "File deleted successfully.")
        Return True
    EndIf

    _Tstbl_MsgBox($MB_OK + $MB_ICONINFORMATION, "File Cleanup", "Deletion cancelled.")
    Return False
EndFunc

Step 2 - Write tests with stubs

In the test file, include TestFramework.au3 - stubs are ready to use from that point on. Use _SetStubReturn() to control what each stub returns, and _StubCallCount() and _GetStubCall() to verify calls. For more readable tests, optionally include StubConstants.au3 - it provides named indexes like $_1st, $_2nd, $_3rd instead of raw numbers, and parameter name constants like $Param_Text, $Param_State instead of raw strings. 

; FileCleanupTests.au3

#include <TestFramework.au3>
#include <StubConstants.au3>  ; optional - named constants for indexes and parameter names
#include "FileCleanup.au3"

Local Const $FILE_CLEANUP_TESTS = "FileCleanupTests.au3"

Func _TestDeleteFileWithConfirmation_FileNotFound()
    _TestFmkHeader("Test: DeleteFileWithConfirmation() - file not found")

    _SetStubReturn("FileExists", $_1st, False)

    Local $bResult = DeleteFileWithConfirmation("C:\temp\myfile.txt")

    _TestFmkAssert($bResult = False,                 "Returns False when file not found",  $bResult,                    False, $FILE_CLEANUP_TESTS)
    _TestFmkAssert(_StubCallCount("MsgBox") = 1,     "Shows one MsgBox",                  _StubCallCount("MsgBox"),     1,     $FILE_CLEANUP_TESTS)
    _TestFmkAssert(_StubCallCount("FileDelete") = 0, "FileDelete not called",             _StubCallCount("FileDelete"), 0,     $FILE_CLEANUP_TESTS)
EndFunc

Func _TestDeleteFileWithConfirmation_UserConfirms()
    _TestFmkHeader("Test: DeleteFileWithConfirmation() - user confirms")

    _SetStubReturn("FileExists", $_1st, True)
    _SetStubReturn("MsgBox",     $_1st, $IDYES)

    Local $bResult  = DeleteFileWithConfirmation("C:\temp\myfile.txt")
    Local $sDeleted = _GetStubCall("FileDelete", $_1st, $Param_Path)

    _TestFmkAssert($bResult = True,                     "Returns True when confirmed",  $bResult,                     True,                 $FILE_CLEANUP_TESTS)
    _TestFmkAssert(_StubCallCount("FileDelete") = 1,    "FileDelete called once",       _StubCallCount("FileDelete"), 1,                    $FILE_CLEANUP_TESTS)
    _TestFmkAssert($sDeleted = "C:\temp\myfile.txt",    "Correct file deleted",         $sDeleted,                    "C:\temp\myfile.txt", $FILE_CLEANUP_TESTS)
EndFunc

Func _TestDeleteFileWithConfirmation_UserCancels()
    _TestFmkHeader("Test: DeleteFileWithConfirmation() - user cancels")

    _SetStubReturn("FileExists", $_1st, True)
    _SetStubReturn("MsgBox",     $_1st, $IDNO)

    Local $bResult = DeleteFileWithConfirmation("C:\temp\myfile.txt")

    _TestFmkAssert($bResult = False,                    "Returns False when cancelled", $bResult,                     False, $FILE_CLEANUP_TESTS)
    _TestFmkAssert(_StubCallCount("FileDelete") = 0,    "FileDelete not called",        _StubCallCount("FileDelete"), 0,     $FILE_CLEANUP_TESTS)
EndFunc

Func _RunFileCleanupTests($bWriteSummary = True)
    Local $bAllPassed = True
	
    $bAllPassed = _TestFmkRun(_TestDeleteFileWithConfirmation_FileNotFound, $bAllPassed)
    $bAllPassed = _TestFmkRun(_TestDeleteFileWithConfirmation_UserConfirms, $bAllPassed)
    $bAllPassed = _TestFmkRun(_TestDeleteFileWithConfirmation_UserCancels,  $bAllPassed)
	
    If $bWriteSummary Then _TestFmkSummary()
    Return $bAllPassed
EndFunc

_TestFmkRunAllTests(_RunFileCleanupTests, $FILE_CLEANUP_TESTS)
Note:
  • Stub indexes are 1-based. StubConstants.au3 provides $_1st, $_2nd, $_3rd, etc. as readable aliases.
  • _SetStubReturn("MsgBox", $_1st, $IDYES) - pre-configures what the first MsgBox call returns.
  • _StubCallCount("MsgBox") - returns how many times a stub was called. Safe even when the stub was never called.
  • _GetStubCall("FileDelete", $_1st, $Param_Path) - reads the path argument of the first FileDelete call.
  • Stubs are reset automatically when _TestFmkHeader() is called. Use _ResetStubs() if you need to reset manually outside of a header call.
  • Never call the function under test directly inside _TestFmkAssert() - capture the result to a local variable first to avoid calling it twice.

Running Multiple Test Suites Together

When a project has multiple test files, a script that includes all test files can execute their test suites together, printing a single combined summary. Use _TestFmk_SetSilentMode(True) to suppress pass and header output across all suites, showing only failures and the final combined summary. Pass $bWriteSummary = False to each test suite function to prevent it from printing its own summary. 

; RunAllTests.au3

#include "MathLibTests.au3"
#include "FileCleanupTests.au3"

_TestFmk_SetSilentMode(True)

Func _RunAllTests()
    Local $bWriteSummary = False
    Local $bAllPassed    = True

    $bAllPassed = _RunMathLibTests($bWriteSummary)     And $bAllPassed
    $bAllPassed = _RunFileCleanupTests($bWriteSummary) And $bAllPassed

    _TestFmkSummary()

    Return $bAllPassed
EndFunc

Exit Not _RunAllTests()

Running Tests from the Command Line

Test suites can be run from the command line. Launching AutoIt3.exe from the command shell does not block the shell until the script finishes, so the shell reads %ERRORLEVEL% before AutoIt has exited. Use start /wait to force the shell to wait: 

start /wait "" "C:\Program Files (x86)\AutoIt3\AutoIt3_x64.exe" "path\to\RunAllTests.au3" > NUL
echo %ERRORLEVEL%

Exit code 0 means all tests passed. Exit code 1 means at least one test failed. The runner script produces this exit code via: 

Exit Not _RunAllTests()

This makes it straightforward to integrate test runs into build pipelines or CI/CD workflows.

Making Scripts Testable

Some scripts have characteristics that require additional steps before they can be included in a test file.

Scripts with an entry point

If the script you are writing tests for calls a function at the top level when executed (i.e. it has an entry point), including it in a test file would execute that code immediately.

1 - Guard the entry point with the framework's test mode sentinel: 

If Not IsDeclared("__TFW_TEST_MODE") Then _Main()
Note: The guard only prevents the entry point from running when the script is included in a test file. When the script is run directly, $__TFW_TEST_MODE is not declared and the entry point executes as normal.

2 - In the test file, just include TestFramework.au3 before the script under test - the sentinel is declared by the framework automatically, preventing the script entry point from running. 

#include <TestFramework.au3>
#include "MyScript.au3"

Scripts that require administrator rights

Scripts that use #RequireAdmin trigger a UAC prompt at interpreted runtime, which breaks testing. Replace it with the compile-time directive - this applies the elevation requirement only to the compiled .exe, not to the interpreted script: 

#pragma compile(ExecLevel, requireAdministrator)

Scripts that use FileInstall

FileInstall requires special handling to be testable. See FileInstall Special Case for details.

Tips

  • Always pass actual and expected values to _TestFmkAssert(). The 3rd and 4th arguments are optional, but without them a failure only tells you the description failed, not what the actual result was. Always include them.
  • Always capture results to a local variable before asserting. Avoid to call the function under test directly inside _TestFmkAssert() - it would be called twice, which can consume extra stub returns or trigger unexpected side effects.
  • Use _StubCallCount() to check how many times a stub was called - it is safe even when the stub was never called.
  • Keep test functions focused. One test function per unit of behavior. If a function has 20 assertions, consider splitting it into smaller, more specific test functions with clearer headers.
  • Name test functions descriptively. _TestAdd_NegativeNumbers() is more useful than _TestAdd2() when reading the console output after a failure.
  • Test both the happy path and the error path. Testing that @error is correctly set on failure is just as important as testing correct return values on success. Always capture @error into a local variable immediately after the call, since any subsequent function call resets it.
  • Write tests first (TDD). AutoIt Test Framework supports a test-first workflow - write the tests before the implementation exists. The test suite will report all failures cleanly without stopping, so you get a clear picture of what needs to be built.
