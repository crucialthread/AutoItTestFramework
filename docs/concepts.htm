Concepts

How the Solution Works

When developing an AutoIt script, the natural instinct is to verify it works by running it and checking the output manually. This works for a while, but as the codebase grows, manual verification becomes slow, error-prone, and incomplete. A change in one function can silently break another, and without a systematic way to check every behavior after every change, regressions go unnoticed until they cause real problems.

Unit tests solve this by encoding expected behavior as code. Each test calls a specific function with specific inputs and asserts that the output matches what is expected. The tests run in seconds, cover every case every time, and fail immediately when something breaks. This makes it safe to change and refactor code - if the tests still pass, the behavior is still correct.

AutoIt Test Framework is a unit test runner for AutoIt. You write test functions that call your code and assert expected outcomes. The framework runs those functions, tracks which assertions pass or fail, prints colored results to the SciTE console, and prints a final summary of totals.

For code that interacts with the user or manipulates external state - showing a dialog, reading or writing files, creating registry entries, building a GUI - the framework also includes testable wrappers and stubs. These allow tests to verify that the right built-ins were called with the right arguments, and to control what those built-ins return, without anything actually executing. No dialog appears, no file is written, no registry entry is created.

The sections below explain each concept in detail.

Basic Test Structure

The core functions for writing and running tests are:

  • _TestFmkHeader() - labels a group of related assertions and resets stubs automatically
  • _TestFmkAssert() - evaluates a condition and records pass or fail
  • _TestFmkRun() - runs a test function and accumulates its result
  • _TestFmkSummary() - prints the final totals
  • _TestFmkSeparator() - prints a separator line to divide groups of tests visually
  • _TestFmkRunAllTests() - runs the test suite only when the script is executed directly
  • _TestFmk_SetSilentMode() - suppresses pass and header output, useful when executing all test suites together

The key design is cumulative pass/fail tracking. _TestFmkRun() takes a test function reference and an accumulated state boolean. It snapshots the current failure count, runs the test, and returns True only if the test passed and no previous test had already failed. The caller chains the return value into the next _TestFmkRun() call, accumulating the result across the whole suite - once any test fails the accumulated state becomes False and stays False, but every test still runs, giving you a complete picture in one run.

The runner function returns the final accumulated state, which reflects the overall suite result. This value can then be translated into a process exit code, making it straightforward to integrate with automated workflows where a build pipeline can check whether any test failed and act accordingly. 

; MyTests.au3

Local Const $MY_TESTS = "MyTests.au3"

Func _TestAdd_ReturnsSum()
...

Func __RunMyTest_Divide(ByRef $bAllPassed)
    _TestFmkSeparator()
...

Func __RunMyTest_Add(ByRef $bAllPassed)
    _TestFmkSeparator()
    $bAllPassed = _TestFmkRun(_TestAdd_ReturnsSum,      $bAllPassed)
    $bAllPassed = _TestFmkRun(_TestAdd_NegativeNumbers, $bAllPassed)
EndFunc

Func _RunMyTests($bWriteSummary = True)
    Local $bAllPassed = True
	
    __RunMyTest_Add($bAllPassed)
    __RunMyTest_Divide($bAllPassed)
	
    If $bWriteSummary Then _TestFmkSummary()
    Return $bAllPassed
EndFunc

_TestFmkRunAllTests(_RunMyTests, $MY_TESTS)

Capturing Results Before Asserting

_TestFmkAssert() evaluates all its arguments before the function body runs. This means calling the function under test directly inside _TestFmkAssert() calls it twice - once when AutoIt evaluates the condition argument, and again when it evaluates the actual value argument.

For simple functions this is harmless. But when the function under test uses testable wrappers internally, each call consumes stub returns that were only configured for one execution. The second call runs with different stub state than the first, so the condition and the actual value passed to the assertion may reflect two different executions rather than the same one, producing misleading results.

It is therefore recommended to always capture the result into a local variable first: 

; Not recommended
_TestFmkAssert(MyFunc(2, 3) = 5, "returns 5", MyFunc(2, 3), 5)

; Recommended
Local $vResult = MyFunc(2, 3)
_TestFmkAssert($vResult = 5, "returns 5", $vResult, 5)

Composable Test Suites

Each test file ends with a call to _TestFmkRunAllTests(), passing the test suite function and the test file name. The framework compares the file name against @ScriptName - the name of the script currently being executed. When they match, the test suite runs. When they do not, nothing happens.

This means the same test file can be executed in two ways without any change to the file itself. Running it directly executes the test suite and prints the results. Including it in a script that includes all test files does not auto-execute the test suite - @ScriptName will be that script's file name, not the test file's, so _TestFmkRunAllTests() will not run the test suite automatically. The script that includes all test files then calls each test suite function explicitly.

This design keeps each test file self-contained and independently executable, while still allowing all test suites to be combined into a single script file and executed together with a shared summary.

Running Multiple Test Suites Together

As a project grows, the number of test files grows with it. Rather than running each file individually, a script that includes all test files can execute their test suites together, producing a single combined summary.

The framework provides _TestFmk_SetSilentMode() to suppress pass and header output across all suites, leaving only failures and the final summary visible. This keeps the output focused on what matters when running all test suites together - if everything passes, a clean summary is enough; if something fails, the failure lines stand out clearly.

A recommended convention for structuring test suite functions to support both standalone and combined execution is to accept a $bWriteSummary parameter. When running standalone the parameter defaults to True and the suite prints its own summary. When called from a script that includes all test files, it is passed as False, delegating the summary to that script which prints a single combined one at the end. Although not a framework requirement, it makes test files flexible and keeps them working both ways without any changes to their code. 

; MathLibTests.au3
...
Func _RunMathLibTests($bWriteSummary = True)
    Local $bAllPassed = True
	
    $bAllPassed = _TestFmkRun(_TestAdd, $bAllPassed)
    $bAllPassed = _TestFmkRun(_TestDivide, $bAllPassed)
	
    If $bWriteSummary Then _TestFmkSummary()
    Return $bAllPassed
EndFunc
...

; RunAllTests.au3

#include "MathLibTests.au3"
#include "FileCleanupTests.au3"

_TestFmk_SetSilentMode(True)

Func _RunAllTests()
    Local $bWriteSummary = False
    Local $bAllPassed    = True

    $bAllPassed = _RunMathLibTests($bWriteSummary)     And $bAllPassed
    $bAllPassed = _RunFileCleanupTests($bWriteSummary) And $bAllPassed

    _TestFmkSummary()

    Return $bAllPassed
EndFunc

Exit Not _RunAllTests()

Testing with Testable Wrappers and Stubs

When a script calls AutoIt built-ins that interact with the user or manipulate external state - such as MsgBox, FileDelete, RegWrite, or GUICreate - those built-ins execute for real during a test run. A dialog appears, a file is deleted, a registry entry is written. This makes it unfeasible to test such code in isolation using assertions alone.

The Testable/Stubs pattern solves this. In script code, _Tstbl_* wrapper functions replace direct built-in calls. In test files, stubs intercept those wrappers recording every call with its arguments and returning controlled values instead of executing the real built-in. The script code itself never changes between normal use and test use. The only difference is whether the wrappers point to the real built-ins or to stubs.

To use _Tstbl_* wrappers in your script, include Testable.au3: 

#include <Testable.au3>

; Without testable wrappers - FileExists and FileDelete execute for real during tests
Func DeleteIfExists($sPath)
    If FileExists($sPath) Then FileDelete($sPath)
EndFunc

; With testable wrappers - FileExists and FileDelete can be intercepted by stubs in tests
Func DeleteIfExists($sPath)
    If _Tstbl_FileExists($sPath) Then _Tstbl_FileDelete($sPath)
EndFunc
Built-in functions and third-party UDFs are already tested and guaranteed by their authors to behave correctly for given inputs. What unit tests should verify is the code built on top of them: whether the right function was called, with the right arguments, and whether the surrounding logic handles the return value correctly, which is exactly what the Testable/Stubs pattern provides.

The Function Pointer Pattern

Every _Tstbl_* wrapper is backed by a global function pointer: 

Global $g_hFn_MsgBox = MsgBox

Func _Tstbl_MsgBox($iFlag, $sTitle, $sText, $iTimeout = 0, $hWnd = 0)
    Local $vResult = $g_hFn_MsgBox($iFlag, $sTitle, $sText, $iTimeout, $hWnd)
    Return SetError(@error, @extended, $vResult)
EndFunc

By default, $g_hFn_MsgBox points to the real AutoIt MsgBox function. When TestFramework.au3 is included in a test file, it automatically reassigns all pointers to stub functions: 

$g_hFn_MsgBox = _Stub_MsgBox

From that point on, any call to _Tstbl_MsgBox() in the code under test goes to the stub instead. The script code never changes - only the pointer changes.

Why a wrapper rather than calling the variable function pointer directly?
_Tstbl_* wrappers are proper AutoIt functions with declared parameters. As such, SciTE picks them up for autocomplete and parameter hints just like any built-in, which calling the variable function pointer globals directly would not.
Besides, they also follow a consistent naming pattern where the _Tstbl_ prefix makes them immediately recognizable while keeping the original built-in name, so they read and behave exactly like the functions they replace.

@error Propagation

AutoIt clears @error after every function call, including a function called through the Return statement. This means a naive wrapper like this loses the error: 

; Wrong - @error from RegRead is cleared when _Tstbl_RegRead returns to its caller
Func _Tstbl_RegRead($sKeyname, $sValuename)
    Return $g_hFn_RegRead($sKeyname, $sValuename)
EndFunc

The correct pattern captures the return value into a local variable, then returns the current @error alongside it through SetError(): 

; Correct - return value captured locally, @error read immediately before anything clears it
Func _Tstbl_RegRead($sKeyname, $sValuename)
    Local $vResult = $g_hFn_RegRead($sKeyname, $sValuename)
    Return SetError(@error, @extended, $vResult)
EndFunc

All _Tstbl_* wrappers follow this pattern. This means code that checks @error after a built-in call works identically when using the testable wrapper.

The Two-Stream Design

Stubs operate on two independent data streams: recorded calls and configured returns.

$g_StubCalls records every call made to a stub automatically. Each entry is keyed by stub type name and 1-based call index, and holds the arguments passed to that call. Tests read from this after running the code under test to verify what was called and with what arguments. Use _StubCallCount() and _GetStubCall() to access recorded calls safely: 

; How many times was FileDelete called?
Local $iCount = _StubCallCount("FileDelete") ; returns 1

; What path was passed to the first FileDelete call?
Local $sPath = _GetStubCall("FileDelete", $_1st, $Param_Path) ; returns "C:\temp\myfile.txt"

$g_StubReturns holds pre-configured return values. Tests write to this before running the code under test to control which branches execute: 

; Make the first MsgBox call return IDYES
_SetStubReturn("MsgBox", $_1st, $IDYES)

The two streams are independent by design. Recording happens automatically on every call. Return configuration is optional - if no return is configured for a given call index, the stub falls back to a default. This means a test can assert on calls without needing to configure returns, and can configure returns without asserting on calls.

Stubs are reset automatically when _TestFmkHeader() is called. Use _ResetStubs() if you need to reset manually outside of a header call.

1-based Indexing

Stub call indexes are 1-based. The first call to any stub is index 1, the second is index 2, and so on. _StubCallCount() returns the total number of calls recorded for a stub type, which also equals the index of the last call: 

; Three FileDelete calls were made
Local $iCount = _StubCallCount("FileDelete") ; returns 3

; Access the first, second, and third calls
Local $sPath1 = _GetStubCall("FileDelete", $_1st, $Param_Path)
Local $sPath2 = _GetStubCall("FileDelete", $_2nd, $Param_Path)
Local $sPath3 = _GetStubCall("FileDelete", $_3rd, $Param_Path)

Use _StubCallCount() to check how many times a stub was called - it is safe even when the stub was never called. 

; Safe way to assert a stub was never called
Local $iCount = _StubCallCount("FileDelete")
_TestFmkAssert($iCount = 0, "FileDelete not called", $iCount, 0, $MY_TESTS)

The same 1-based convention applies to _SetStubReturn() - index 1 configures the return for the first call, index 2 for the second, and so on. StubConstants.au3 provides named aliases ($_1st, $_2nd, $_3rd, etc.) for these indexes.

Preventing Entry Point Execution in Test Files

Scripts that have an entry point (a top-level function call that starts execution) must guard that entry point so test files can include them without triggering execution. Use the framework's built-in sentinel constant $__TFW_TEST_MODE: 

If Not IsDeclared("__TFW_TEST_MODE") Then _Main()

In the test file, just include TestFramework.au3 before the script under test - the sentinel is declared by the framework automatically, so no manual declaration is needed: 

#include <TestFramework.au3>
#include "MyScript.au3"

This works because TestFramework.au3 declares $__TFW_TEST_MODE as a global constant at include time. When the script under test is run directly, TestFramework.au3 is not included, so $__TFW_TEST_MODE is never declared and IsDeclared("__TFW_TEST_MODE") returns False - the entry point runs as normal. When the script is included in a test file that starts with #include <TestFramework.au3>, the constant is already declared by the time the guard is evaluated, so IsDeclared("__TFW_TEST_MODE") returns True and the entry point is skipped.

This is why TestFramework.au3 must always be included before the script under test in a test file - if the order were reversed, the guard would evaluate before $__TFW_TEST_MODE is declared and the entry point would run.

Not all scripts need this guard. Library scripts that only define functions and declare globals have no entry point and can be included in test files directly. The guard is only needed when a script calls a function or runs code at the top level.
